# Authentication invariants

The five-word passphrase is the product's only credential. These rules are what
keep 137 existing workspaces able to log in. Read this before editing
`lib/auth/passphrase.ts`, `lib/validations/schemas.ts` or
`app/api/workspaces/access/route.ts`.

This file is tracked deliberately. It previously lived only in an untracked,
gitignored `CLAUDE.md` on one laptop, which meant the rules that stopped the
login path being broken travelled with nobody.

## 1. Never normalize the passphrase before hashing, verifying or looking up

Do not lowercase, strip accents, or otherwise transform the passphrase on its
way into `hash`, `verify` or `computeLookup`. The dictionary is not ASCII: of
the 7,776 entries in `diccionario/palabras.ts`, 1,427 carry an accent, 28
contain uppercase (`José`, `ADN`, `Berlín`), 2 contain `ü` (`antigüedad`,
`vergüenza`), 1 contains an underscore (`al_menos`) and 1 contains a space
(`tal vez`). Stored hashes were computed over the exact bytes. Normalizing
would lock every existing workspace out.

## 2. Input repair happens through dictionary candidates, never normalization

A mobile keyboard capitalizes the first word and drops accents. The correct
repair is `candidatePassphrases`, which reconstructs the original words from
the dictionary and tries each one. It touches no stored hash.

## 3. `repairKey()` normalizes on purpose, and that does not violate rule 1

`repairKey` exists only to *index* the dictionary — `"Año"` becomes `"ano"` so a
mangled word can find its original. Its output never reaches `hash`, `verify` or
`computeLookup`. What `candidatePassphrases` returns are the dictionary's
original, byte-exact words, and the phrase exactly as typed is always candidate
number zero.

If someone deletes `repairKey` because it looks like the normalization rule 1
forbids, repair breaks while every hash test still passes. That is why this rule
is written down.

## 4. `generate()`, `hash()`, `verify()` and `computeLookup()` are byte-frozen

Stored hashes were produced by these exact functions. Changing what they feed
into bcrypt or HMAC invalidates every credential in the database.

## 5. Every attacker-controlled input on this path needs an upper bound

`PassphraseSchema` caps length at 200 characters and word count at 12, and
`candidatePassphrases` carries its own independent 12-word backstop plus
`MAX_CANDIDATES`. Without these, candidate expansion overflows the stack and
also dilutes the rate limiter beyond its accepted bound.

## What the tests protect

`__tests__/lib/auth/passphrase.test.ts` asserts these premises directly. If one
of those tests fails, a premise changed — do not relax the test.

## Facts already verified, so they are not re-derived

- The cap can never truncate a legitimate passphrase out of the candidate list:
  18 dictionary keys collide, all two-way, so a real five-word passphrase yields
  at most 2^5 = 32 candidates against a ceiling of 64.
- bcrypt runs at most once per request: `passphrase_lookup` is unique and
  indexed, so each candidate matches at most one row.
- `401` and `500` responses leak no workspace-enumeration signal.
- No passphrase is ever user-chosen; all are generated by CSPRNG over
  7,776^5 ≈ 2.85×10^19.

## Accepted risk

One request tests up to `MAX_CANDIDATES` guesses but records a single
rate-limit attempt, diluting the guess budget up to ~64×. Accepted only because
passphrases are server-generated over that keyspace. **Revisit immediately if
passphrases ever become user-chosen** — that assumption is the entire basis.
